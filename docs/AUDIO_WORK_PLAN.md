## 단계 A: 추출과 시간 정합

1. 명시적 `--video` 경로를 받는다. 첫 번째 MP4를 무조건 선택하지 않는다. 원본 파일 SHA-256을 `source_id`로 사용한다.
2. 원본 메타데이터·스트림 start_time·time_base·샘플레이트·채널·duration·추출 명령·도구 버전을 manifest에 기록한다.
3. 우선 약 3~12초를 분석한다. 가능하면 원본 오디오를 PCM으로 디코딩한 뒤 샘플 인덱스로 구간을 자른다. seek·AAC priming·리샘플링·필터 지연으로 생기는 시간 오차와 처리 방식을 확인한다.
4. 원본 디코딩 샘플레이트·스테레오를 보존한 자료와 분석용 자료를 분리한다. 모노 변환·리샘플링은 설정과 채널 상쇄 영향을 기록한다. 주파수 정보가 필요한 분석을 낮은 샘플레이트로 무조건 통일하지 않는다.
5. 모든 이벤트 시간은 원본 영상 재생 기준 초로 출력한다. 로컬 클립 시간·샘플 인덱스·원본 시간을 연결하는 오프셋을 저장한다. 프레임 번호/24만으로 오디오 정합을 끝내지 않는다.
6. 파형과 영상의 명확한 스트로크 3곳 이상을 비교해 동기화 오차를 측정한다. 최초 목표는 오차가 영상 1프레임(약41.7ms) 이내인지 확인하는 것이다. 프레임 판독 한계를 함께 보고하고 불명확하면 보정값을 확정하지 않는다.

## 단계 B: 음향 기준선

- 파형·에너지·스펙트로그램과 onset 후보를 만든다. 창 길이·hop·분석 지연을 저장한다. 짧은 프레임의 기본 주파수 해상도 한계를 설명한다.
- 단음이 뚜렷한 구간은 기본 주파수 후보를 검증한다. 스트로크 화음에는 단음 피치 추정기를 그대로 적용해 한 음으로 확정하지 않는다.
- 다성 구간은 chroma/pitch-class salience와 복수 음높이 후보를 출력한다. 배음·옥타브 오류를 오류 사례로 남긴다. chroma만으로 옥타브·현 번호를 복원하지 않는다.
- 음높이 후보에는 MIDI 또는 주파수, 시작·끝 후보, score와 그 의미를 기록한다. offset은 단순 감쇠 임계값으로 확정하기 어려우면 별도 추정 상태로 둔다.
- 스트로크·뮤트성 타격의 광대역성·감쇠 특징을 탐색하고 acoustic event 후보로 출력한다. 강한 일반 피킹 어택과 구분이 안 되면 unknown으로 둔다.
- 음 없음은 미연주·뮤트·작은 신호·검출 실패 모두 가능하다. silence를 muted로 자동 변환하지 않는다.
- 신뢰도는 측정 전에는 휴리스틱 score다. 가우시안 질량이나 정규화 salience를 보정된 실제 확률로 부르지 않는다.

## 단계 C: 현 상태 결합을 위한 증거 제공

손·튜닝·카포에서 예상하는 음과 비교할 수 있도록 주파수/옥타브를 보존한다. 동일 음을 여러 현에서 낼 수 있으므로 오디오 단독으로 `string_num`을 확정하지 않는다. 검출되지 않은 음을 특정 현의 뮤트 증거로 사용하지 않는다.

후속 통합 단계는 다음 두 축을 별도로 관리한다.

| 축 | 상태 |
|---|---|
| 손·현 관계 | open / fretted / light_touch / unknown |
| 음향 상태 | pitched / percussive / silent / unknown |

이 담당은 두 번째 축의 시간별 증거를 제공한다. `percussive`가 실제 의도적 뮤트인지, 어떤 현인지, 손바닥·왼손 중 어디에서 발생했는지는 통합 단계가 판단한다. 카포로 열린 현은 원래 개방현과 음높이가 다르므로 튜닝과 카포는 별도 메타데이터로 받는다.

## 화성 담당과의 교환 계약

제안 공통 버전은 `guitar_evidence.v1`이다.

| 필드 | 의미 |
|---|---|
| `schema_version`, `run_id`, `source_id` | 버전·실행·원본 MP4 SHA-256 |
| `start_s`, `end_s`, `timebase` | 원본 영상 시간, 구간 [start,end), timebase=`source_video_seconds` |
| `tuning`, `capo`, `assumptions` | 확인된 설정과 미확인 가정 |
| `evidence`, `provenance`, `limitations` | 특징·설정·근거 파일·제약 |

오디오 출력은 `onsets[]`, `pitch_candidates[]`, `pitch_class_salience[]`, `acoustic_events[]`, `status`를 포함한다. 이벤트는 `event_id`, `start_s`, `end_s`, `score`, `score_type`, `method`와 상태를 갖는다. 음높이 후보에는 `midi`/`frequency_hz`, `pitch_status`와 오차·분해능 정보를 추가한다. 원시 onset이 점 사건이면 `time_s`를 사용한다. 프레임별 특징에는 frame 시작/중심 중 어떤 시간을 쓰는지 명시한다.

화성 담당은 이 음향 증거로 코드 후보를 계산한다. 오디오 파일 안에 화면의 정답 코드명을 예측 결과처럼 넣지 않는다. 참조는 별도 `references/`에 두고 알고리즘 입력과 분리한다.

## 검증과 산출물

제안 CLI:

```powershell
python audio_extract.py --video "<원본 MP4 절대 경로>" --start 3 --end 12 --output dataset/audio_analysis/runs/clip_003_012
python audio_analysis.py --manifest dataset/audio_analysis/runs/clip_003_012/manifest.json
python -m unittest test_audio_analysis -v
```

제출할 결과:

1. 추출 코드·manifest·파형/스펙트럼 시각화·재생 가능한 짧은 검토 클립. 원본은 보존한다.
2. 시간별 JSON, 화성 담당용 최소 입력 fixture, 스키마 문서.
3. 알려진 단음·혼합음·침묵·감쇠·타격 신호의 의미 있는 합성 시험. 합성 시험 통과를 실연 성능으로 주장하지 않는다.
4. 실제 클립의 수작업 onset·음높이 참조 및 독립 검수 여부. 알려진 TAB를 그대로 실제 오디오 정답으로 복사하지 않는다.
5. `dataset/audio_analysis/report.md`: 동기화 오차, onset 오차·정밀도·재현율(초기 허용 오차±50ms, 일대일 매칭), 피치 옥타브 오류, 누락·오탐·뮤트성 이벤트 한계, 실행 명령·처리 시간.
