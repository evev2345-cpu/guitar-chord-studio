## 공동 목표와 우선순위

**3~12초에서 영상·음향 증거·화성 후보를 동일 시간축에 나란히 표시하는 통합 데모**를 다음 목표로 한다. 먼저 계약·시간 정합을 해결하고 모듈 정확도를 개선한다. 전체 곡 확장·TAB 출력·기능화성·완전 현별 접촉 분류는 후순위다.

검증 상태: Python59개 통과. 실제 오디오→화성 입력은 capo null에서 크래시한다. 실제 피크는 확정 음이 아니며 실연 정답도 없다. 각 담당은 자기 모듈과 자기 보고서를 수정하고 다른 담당의 파일·공용 README를 동시에 수정하지 않는다. 새로운 결과는 별도 run 폴더에 저장한다.

## P0 — 화성 담당에게 전달

1. `harmony_engine.py`에서 capo 누락/null/unknown 객체를 일관되게 처리한다. 알 수 없는 카포는 음0개·보류로 남기되, 입력에 독립적인 실제 MIDI 증거가 있으면 그 음으로 화성 계산은 가능해야 한다.
2. 실제 `dataset/audio_analysis/runs/clip_003_012/evidence.json` 구조의 최소 fixture를 고정하고 어댑터 회귀 검사를 추가한다. 기존 합성 계약만으로 통합 성공을 보고하지 않는다.
3. 오디오의 spectral_peak_candidate를 observed_audio_notes로 승격하지 않는다. 실제 음이 미확인일 때는 크래시 없이 후보 증거와 insufficient_evidence를 반환한다.
4. 오디오 담당과 창·시간·event_id·score_type·pitch_status 계약을 맞춘다. 확정/잠정 음과 salience를 각각 다룰 입력을 설계한다. 점수를 확률로 표시하지 않는다.
5. 서로 다른 시간의 음을 한 화음으로 합치지 않도록 time-local 구간 입력을 검증한다. 최초에는 검수된 안정 구간을 명시 입력받아도 된다. 구간 선정 출처를 보존한다.
6. 두 pitch class는 화음 확정에 불충분하다는 현 정책을 문서화하되, power chord를 지원한다면 명시적인 5 후보/모호성 출력으로 구현하고 시험한다. 조용히 임계값만 낮추지 않는다.

제출: 실제 오디오 계약 재생 시 오류0, spectral 후보는 미확정 유지, 시간 구간별 후보/보류 JSON, 동작 전후 회귀 결과와 수정한 계약 문서. 파일 소유는 harmony 계열이다.

## P0 — 오디오 담당에게 전달

1. 실제 원본 PTS와 원본 재생 시간의 매핑을 검수한다. 시작 PTS 차와 실제 A/V 동기 오차를 구분하고, 명확한 스트로크3곳 이상에서 파형·영상 대응을 기록한다. 새 출력에는 보정 전후 시간과 근거를 남긴다.
2. 청취 가능한 방식으로 3~12초를 검토하고 기타 외 반주·보컬 혼합 여부를 기록한다. 환경에서 청취할 수 없으면 검토용 클립과 라벨 양식을 제공하고 해당 평가를 보류한다. 청취하지 않고 수행했다고 보고하지 않는다.
3. 화면 악보와 분리해 실제 onset·안정된 음높이 일부를 수작업 검수한다. 최초 목표는 명확한 onset10개와 검수 가능한 안정 창3개다. 구간에 충분한 사례가 없으면 실제 개수·사유를 보고하고 수치를 채우려고 추측하지 않는다.
4. onset용 짧은 창과 저음 피치용 긴 창을 분리하는 변경을 검토한다. 현185.8ms 창의 flux 중심시간은 10ms hop과 같은 onset 정확도가 아니다. 검수 전후 onset 오차·오탐·누락으로 변경 효과를 판단한다.
5. 반복 spectral peak10,177개를 음표 수로 집계하지 않는다. 배음/옥타브 문제와 시간 지속성을 검토하고 잠정 음 또는 pitch-class 증거를 생성한다. 확정 기준이 없으면 후보 상태를 유지한다.
6. 화성 담당에게 작은 실제 구간 fixture를 제공한다. `capo=null`은 정상 계약임을 명시하고 미확인 튜닝/카포를 코드 표기에서 가져와 확인된 값으로 바꾸지 않는다.

제출: PTS 대응표, 청취 여부와 혼합 상태, 정답/보류 라벨, onset±50ms 일대일 평가, time-local 피치 증거와 한계. 파일 소유는 audio 계열이다.

## P1 — 지판·프렛·현 담당에게 전달

1. 공동3~12초에서 대표 프레임을 선정하고, 지판 기하가 프레임별 유효한지 검사한다. 최소 초기·중간·끝과 큰 이동 시점을 포함한다. 수동 fixture를 사용하면 그대로 수동 출처를 표시한다.
2. 너트·카포·물리 프렛·상대 프렛 관계를 검수한다. 카포를 너트 또는 금속 프렛 와이어로 잘못 쓰지 않는다.
3. 부분 선 검출에서 물리 현 번호를 강제하지 않는다. 관측 가능한 선의 독립 원본 참조를 늘리고, 현 정체성은 경계 방향/연속 관측/수동 검수 중 어떤 근거인지 표시한다.
4. 공통 프레임 식별자를 채택한다: `source_id`=원본영상 SHA-256, `frame_index`, `frame_pts_s`, `frame_pixel_sha256`=decoded BGR 배열의 해시, `image_file_sha256`=저장 파일의 해시. 기존 source_id의 사례 이름은 case_id로 구분하고 하위 호환 변환을 둔다.
5. 지판 재사용의 유효/의심/불명 상태를 손 담당에게 전달한다. 움직임이 작다는 이유만으로 정확한 프렛·현을 확정하지 않는다.

제출: 같은 구간의 번호·기하 출처가 명확한 현/프렛 JSON, 원본 오버레이, 기하 유효성 기록과 실패 사례. 완전6현 미달은 실패를 숨기지 말고 부분 검출로 보고한다.

## P1 — 손 담당에게 전달

1. 공동 구간을3~12초로 맞춰 같은 프레임 식별자·PTS를 사용한다. 기존217초 오류 구간은 회귀 자료로 계속 보존한다. 전체 영상을 먼저 돌리지 않는다.
2. 현 담당의 지판 유효성 상태를 사용하고, 미검증 fixture에서는 접촉·정확한 프렛 결정을 보류한다.
3. 검수126점을 모두 채우는 작업 전에 대표 오픈/바레/오류 프레임3장의 가시 손목·손끝·검지 관절부터 독립 검수를 진행한다. hidden/unknown은 좌표를 추측하지 않는다. 예측을 숨긴 기존 HTML과 JSON 입력을 이용한다.
4. 실제 검수자가 채우지 않은 값은 에이전트 시각 참조로 유지한다. 사람이 필요하면 필요한 최소 검수 항목을 구체적으로 제시하고 자동 처리 가능한 작업은 계속한다.
5. 고정6px·속도180px/s·ROI 일치 gate의 보류율과 명확한 정상 장면의 과도한 보류를 함께 측정한다. 모든 판단 보류가 정확도 향상을 뜻하지 않는다.
6. 후보와 원시 관측을 보존한다. 이번 단계에서 영구ID·복잡한 평활화보다 현·손·프렛 정합과 오류 감지에 집중한다. 비접촉 손가락을 코드 구성음으로 만들지 않는다.

제출: 같은 구간의 관측/후보/보류 상태와 오버레이, 독립 검수 현황, 오류/과도한 보류 사례. 파일 소유는 hand/sequence/review 계열이다.

## 통합 책임과 완료 기준

총괄은 다음 접점만 별도 통합 계층에서 관리한다. 담당별 확정 규칙을 다른 모듈에 복제하지 않는다.

1. 원본 해시·프레임 PTS·오디오 시간을 검증하고 서로 다른 원본은 결합을 거부한다.
2. 동일 구간의 손/현/프렛과 음향 증거를 나란히 출력한다. 악보·코드 화면 참조는 별도 평가 레이어로 표시한다.
3. 현 상태는 손 관계(open/fretted/light_touch/unknown)와 발음(pitched/percussive/silent/unknown)을 별도로 보존한다. 침묵→뮤트, 후보 위치→접촉으로 단정하지 않는다.
4. 확정 음의 코드 후보와 위치·음향 가정에 따른 코드 가설을 구분한다. 증거가 모자라면 보류하되 코드 엔진 자체는 검수된 음 fixture로 독립 검증 가능해야 한다.
5. 다음 공동 완료 기준은 실제 오디오를 넣어도 크래시0, 원본/시간 정합 근거 존재, 참조 정답 유입0, 원시 후보·출처 보존, 대표 정상/실패/보류 사례를 한 화면 또는 한 보고서에서 검토 가능한 상태다.

이 문서는 전달용 지시다. 총괄 리뷰 과정에서 다른 채팅에 메시지를 전송하거나 새 작업을 자동 시작하지 않았다.
