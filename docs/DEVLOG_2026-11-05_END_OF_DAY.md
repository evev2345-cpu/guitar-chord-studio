195~225초의 손 선택과 현재 프레임의 잠정 지판을 연결했다. 기존 오디오는3~12초뿐이어서194~226초 원음을 PTS/샘플 정합으로 추출하고 로컬 Demucs로 보컬 제거 반주를 생성했다.18시점의 탐색80/20 통합에서는1위1곳, 상위3개7곳이 바뀌었다. 이 단계는 정답 없이 후보 변화만 비교한 것이다.

### 화면 정답 대조와 안정 구간 재평가

사용자 지적에 따라 손 실패 진단용 시점을 정확도 표본으로 사용하던 방식을 보완했다.195~225초를2초 간격으로16곳 검토하고, 앞뒤 약0.208초 사진에서 운지/표시 전환이 의심되는7곳을 제외했다. 안정구간9개에서 화면 코드·TAB·다이어그램과 실제 손을 대조한 에이전트 참조정답을 저장했다. Capo.1을 반영해 화면F# 운지를 실음G로 비교했다. 표준튜닝은 가정이며 별도 독립 청음 전사 정답은 아니다.

기존 반주와 반주+손은 정확한 코드1위2/9, 상위3개 정답포함6/9, 근음8/9로 같았다. 해당 결과와 구간 선정/라벨의 한계는 별도 보고서에 남겼다.

### 기타 추정 트랙 분리

공식 htdemucs_6s 모델을 기존 격리 환경에 추가 캐시했다. 가중치 약54.9MB, SHA256/리비전 경로를 기록했고 패키지를 새로 설치하지 않았다. 같은32초 원음에서 기타 추정 트랙을 직접 분리했다.

기타 트랙은 정확한 코드1위2/9를 유지하면서 상위3개 정답포함7/9, 근음9/9로 일부 개선됐다. 손 정보를 더해도 이 수치는 같았다. 사용자가 재생한198~202초 발췌에 대해 “기타만 잘됐어”라고 확인했고 해당 파일SHA256에 연결한 청음 검수 기록을 저장했다. 전체32초/정량 누출/음높이 검수로 확대하지 않았다.

### D2~E6 컷과 가중치 전수 비교

사용자 요청대로 기타 트랙에73.416~1,318.510Hz 컷을 적용하고, 피크 후보에도 같은 경계를 적용했다. D2 하한은 드롭D 튜닝 가정 변경이 아니다. 비전:오디오1:9~9:1 및 비교용0:10·10:0을 검사했다.

| 비전:오디오 | 컷 전 정확1위 | 컷 후 정확1위 | 컷 후 상위3개 정답포함 |
|---|---:|---:|---:|
|1:9|2/9|3/9|7/9|
|2:8|2/9|3/9|7/9|
|3:7|2/9|2/9|7/9|
|4:6|2/9|2/9|6/9|
|5:5|2/9|2/9|5/9|
|6:4|1/9|1/9|3/9|
|7:3|1/9|1/9|2/9|
|8:2|1/9|1/9|2/9|
|9:1|1/9|1/9|1/9|

컷 후2:8은 정확한 코드3/9(33.3%), 상위3개7/9(77.8%), 근음9/9를 보였다. 컷만 한0:10도 정확1위3/9였으므로 비전이 추가 정답 수를 늘린 것은 아니다. 컷만 하면195초 근음이 틀렸는데2:8에서 복구됐다.199초는 컷으로Gmaj7→G가 됐지만 비전을3:7 이상 주면Gadd9로 다시 틀렸다. 상위 비전 비중이 오디오 정답을 덮는 사례를 보관했다.

### GuitarSet·EGDB 검사

- GuitarSet: JAMS360개(반주180/솔로180), 줄별 음표62,476개가 있고 대응 녹음 음원은 없다.
- 모든 JAMS에 기본 악보 코드와 상세 연주 코드가 별도 층으로 있다. 이를 혼합하지 않고 실제 음표 정답과 함께 평가해야 한다.
- EGDB 실제 로컬 폴더는 `EGDB_repo`다. 전체 연구 데이터가 아닌 데모 사이트 저장소이며 WAV18개(Training8/RealData5/모델출력5)만 있고 대응 MIDI/음표 정답이 없다.
- 둘 다 현재 구성에 손 영상 정답은 없어 오디오 모듈 검증용이며 실제 비전:오디오 가중치의 독립 검증셋으로 바로 쓰지는 못한다.

![GuitarSet 실제 음표와 기본/상세 코드 주석](../dataset/integration_review/runs/reference_dataset_audit_20261105_v1/annotation_example.png)

공식 다운로드 페이지는 [GuitarSet Zenodo v1.1.0](https://zenodo.org/records/3371780)다. 우선 `audio_mono-mic.zip` 약657MB를 안내했다. 필요 시 줄별 분석용 `audio_hex-pickup_debleeded.zip` 약3.6GB를 추가 검토한다. 에이전트가 새 데이터 다운로드를 시작한 상태는 아니다.

## 검증

최종 코드 변경까지108개 테스트를 통과했다.

`python -m unittest test_bandcut_weight_sweep test_audio_analysis test_guitar_stem_comparison test_tutorial_reference_evaluation test_new_hand_harmony test_harmony_engine test_cell_audio_fusion test_hand_cell_distribution test_virtual_string_grid test_global_fretting_hand -q`

검사 범위는 대역 필터/피크 경계, 고정9개 정답과 시각질량 보존, TAB+카포 이조, 같은 시간/샘플/원본 해시 정합, 기존 반주 점수 재현, 지표 재계산, 미확정 의미/기하 차단 등이다. 테스트 통과와 실제 코드 정확도는 별개다. 데이터셋 감사 스크립트도 전체360개 주석과18개WAV를 읽어 통계를 저장했다.

## 다음 작업: 재개 순서

1. `audio_mono-mic.zip`이 준비되면 파일 해시/ZIP 구성/음원 수를 검사하고 기존 JAMS와 파일명으로 연결한다. 원본 파일은 유지한다.
2. GuitarSet의 기본 코드와 상세 코드 층을 구분하는 평가 어댑터를 만든다. 줄별 실제 음표 정답을 우선 사용해 기본음/배음 오인식과 누락음을 측정한다. 현재 도우미 `inspect_jams.py`가 두 코드 층을 합치는 점은 평가 경로에서 수정해야 한다.
3. 같은 진행/연주가 학습·조정·평가에 섞이지 않도록 분할을 정한다. 현재 영상9개로 고른2:8을 독립 최적값으로 간주하지 않는다.
4. G/Gmaj7, A/Amaj7 같은 오판을 기본음 근거·배음·추가음별 점수로 분석한다. 확장음 억제를 시험할 때 실제7코드를 잘못 단순화하지 않는지도 확인한다.
5. 오디오가 개선된 뒤 별도 영상/구간에서 비전 결합을 다시 검증한다. 손 위치를 이용한 기본음 후보 사전과 최종 코드점수 가중치 스윕은 서로 다른 실험으로 관리한다.
