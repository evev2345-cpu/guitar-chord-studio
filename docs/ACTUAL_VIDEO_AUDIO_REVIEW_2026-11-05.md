## 화면 읽는 법

원본1280×720영상은 그대로 두고 아래에220픽셀 분석 패널을 붙였다. 손과 기존 코드·TAB를 가리지 않는다. 왼쪽은0.2초고정창, 오른쪽은0.4초고정창으로 모은 오디오 후보다. 큰 글씨는1위, 아래는2·3위다. 동점은 별도로 표시한다.

‘실음’은 오디오에서 추정한 코드, ‘운지표기’는 화면과 비교하기 위해 카포1을 반영해 환산한 코드명이다. **운지표기는 손가락을 검출해 얻은 결과가 아니다.** 표준튜닝·카포1 가정을 사용했다.

재생 페이지에서 원본 소리와 기타 추정음을 바꿀 수 있다. 영상의 판별 결과는 두 재생 모드에서 동일하며, 실제 판별에는 기타 추정음을 사용했다. 원본 혼합음을 판별한 결과처럼 표시하지 않았다.

211초에서 화면 운지G#는 실음A다.0.2초는A를 고르고0.4초는Amaj7을 고르는 실패를 그대로 보여준다. 원본 사진은 관측, 아래 후보는 모델 추정, 하단 검수 참조는 기존 분석자 판독을 구분했다.

257초는 반대로0.2초가Dm,0.4초가Dm7을 고른다. 화면 운지C#m7에카포1을 반영한 참조는Dm7이다.0.4초에는 최고점 동점도 있으므로 맞춘 코드 하나가 유일하게 확정됐다는 의미는 아니다.

## 실행한 경로

기타추정트랙 → 기존사전학습Basic Pitch → 음후보D2~E6제한 → max0.2/0.4초 → 기존coverage코드채점 → 영상프레임별표시.

추가 보정 학습과 변화경계 제한은 이번 재생 자료에 적용하지 않았다. 별도 후보 안정화나 정답에 맞춘 교체도 하지 않았다. 최소3종류의음근거가없으면보류한다. 음원 경계에서 전체 시간창을 확보하지 못한 프레임도 구분해서 표시했다.

검수 참조는 기존9곳과 새4곳의 확인된 시각 주변에서만 표시한다. 그외시점에 새로운정답을임의로붙이지않았다. 참조는화면코드/TAB/보이는운지를대조한분석자판독이고독립청음전사나두번째사람의검증은아니다. 정답은모델입력이나순위에들어가지않는다.

## 검증

- 원본 영상SHA256을 기존 수신자료와 대조했다.
- ffprobe의실제영상PTS로프레임을선택했다.194~226초768프레임,250~266초384프레임이며24fps간격을검사했다.
- 원본픽셀을그대로렌더입력에썼는지211초·257초PNG상단720픽셀을원본디코딩프레임과전수픽셀비교했다. 일치했다. 최종MP4는H.264손실압축이므로픽셀동일을주장하지않는다.
- 원본/기타소리버전모두H.264/AAC, 영상·음원시작0초, 각각32/16초 길이일치를검사했다. 모든완성MP4를FFmpeg로전체디코딩해오류가없는지확인했다.
- 오디오는 기존 샘플정합 추출 WAV를 사용했다. 영상에 맞추려고 오프셋을 피팅하지 않았다. 컨테이너 정합이 모든 실제 시청각 지연을 보장하지는 않는다.
- 프레임별추론값·원본프레임번호·PTS는각timeline.json, 입력해시와조건은manifest.json, 픽셀/시간간격검사는render_audit.json에있다.

실시간시스템이아닌오프라인재생검수자료다. 모델의약2초문맥과중심시간창에미래오디오가포함된다. 손·지판 결합이나 실제현접촉판정은 추가하지 않았다.

재현: `python render_audio_video_review.py`. 완료된 출력 폴더를 덮어쓰지 않으므로 다시 만들 때는 새OUT경로를 지정한다. 첫10초 자료는 기존32초 영상에서11초지점부터10초를정확탐색후재인코딩해만들었다.

다음 검수에서는 연속 재생에서 코드가 자주 바뀌는 부분,7음이빠지는부분,추가텐션이붙는부분을 영상시각으로 기록한다. 먼저 실제 재생을 확인하고 추가 알고리즘 변경을 결정한다.
