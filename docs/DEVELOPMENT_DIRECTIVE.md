# GUITAR 개발 총괄 지시서

기준일: 2026-11-02 / 현재 파일과 로컬 검증 결과에 근거한 개발 결정.

## 1. 제품 목표와 현재 판정

장기 목표는 기타 연주 영상·오디오에서 검토 가능한 TAB 초안을 만드는 것이다. 기존 코드와 데이터 구성에서 도출한 목표이며, 사용자 제품 요구사항으로 확정된 것은 아니다.

첫 출시 범위는 **정지 이미지의 지판·프렛·손가락 위치 후보를 사람이 검토하고 수정할 수 있는 분석 도구**로 고정한다. 실제 현 접촉이나 음표를 확정했다고 표시하지 않는다. 현재 단계는 연구 프로토타입이며, 정확도 검증과 재현성을 갖추는 것이 다음 개발 목표다.

개발 순서: 재현 가능한 실행 → 정답 데이터 → 정지 이미지 품질 → 영상 추적 → 현·접촉 검증 → 오디오 결합·TAB.

## 2. 확인 범위와 근거

- 기존 파일 1,253개, 총 854,882,057바이트를 목록화했다. `file_inventory.csv`에 경로·크기·검사 방식·SHA-256을 기록했다. 생성한 docs와 캐시, 내부 .git은 집계에서 제외했다.
- Python 57개를 AST로 파싱했다. JSON/JAMS/ipynb 495개를 파싱하고 기타 텍스트 102개를 읽었다. 이 검사에서 구문 오류는 없었다. 구문 정상은 실행·의미적 정확성을 보장하지 않는다.
- 바이너리 598개는 목록·크기·해시 검사다. 전체 이미지 육안 검수, 전체 오디오 청취, 가중치 재학습·전체 노트북 실행은 하지 않았다.
- `.env`는 내용 검사와 해시 공개에서 제외했다. 외부 API 호출, 유료 재평가, 서버 실행, 학습은 수행하지 않았다.
- `python -m unittest test_hand_fret_tracker test_fret_geometry test_baze_client -v`: 22개 통과.
- 프로젝트 루트의 `git status`는 Git 저장소가 아니라는 오류를 반환했다. 상위 관리 체계가 별도로 존재하는지는 미확인이다.

## 4. 표준 분석 파이프라인

1. **입력 등록:** image_id, 원본 SHA-256, 이미지 크기, 출처, 촬영 그룹, 좌우 반전 여부, 튜닝·카포의 known/unknown을 기록한다.
2. **지판 검출:** 전체 이미지 후보 박스 → 여유 영역 crop → 정밀 코너. 실제 API 호출은 코너 2회와 프렛 1회로 기본 3회다. 유효성 실패 시 원인과 응답을 보존한다.
3. **좌표 변환:** named corner → homography → 자연색/보정 평탄화 영상. 변환 행렬과 캔버스 크기를 반드시 함께 저장한다.
4. **프렛 분석:** 관측 선분 검출 → 번호·좌표·순서 검사 → 내부 보간 → 조건부 경계 추정. observed/interpolated/boundary_estimated/rejected/unresolved를 구분한다.
5. **손 분석:** 원본 이미지에서 손 검출 → 지판 근접성 기반 손 선택 → 평탄 좌표 투영 → 프렛 칸 후보. 선택 모호·손 없음·기하 불량은 정상적인 명시 상태다.
6. **검토:** 원본·평탄화·출처별 색상·실패 이유·수정 UI를 출력한다. 균등 현 밴드는 추정임을 표시하고 기본적으로 확정 현 번호를 출력하지 않는다.
7. **산출물:** 결과 JSON, 오버레이, API 사용량, 실행 manifest를 같은 run_id로 연결한다. 성공률과 정확도를 분리 집계한다.

영상 단계에서는 지판을 초기/재검출 시점에 찾고 프레임 사이에는 로컬 추적을 사용한다. 모든 프레임을 VLM에 보내지 않는다. 추적 오차·가림·카메라 이동으로 품질이 낮아지면 재검출하고, 재검출 전까지 unknown을 유지한다.

## 5. 데이터 계약의 우선 수정

현재 JSON에는 좌표 규약과 캔버스 정보가 충분히 자가 설명적이지 않다. 다음 버전은 아래를 포함한다.

- `schema_version`, `run_id`, `image_id`, 원본 해시·크기, `canvas_size`, `M`, `M_inv`, corner 이름·좌표계.
- `source`는 검출 경로, `visibility`는 가림 상태, `numbering_status`는 번호 확정 여부로 분리한다. occluded를 모든 불확실성의 대용어로 사용하지 않는다.
- `physical_fret_num`은 확인 불가 시 null로 둔다. 정렬용 `wire_id`와 분리한다. 기존 정수 번호 필수 기하 계약은 버전 변환기로 연결하고 호환성을 검사한다.
- 손 결과는 `candidate`와 `contact`를 별도 필드로 둔다. 실제 접촉을 측정하지 않은 결과는 `contact=unknown`이다.
- 모델 ID·프롬프트 해시·예시 해시·전처리 설정·패키지 버전·실행 시간·사용량·실패 원인·재시도 이력을 저장한다.
- 캐시 재사용 키는 이미지·모델·프롬프트·예시·설정·스키마의 해시 조합으로 만든다. 과거 결과를 수정하지 말고 새 버전 산출물을 생성한다.

**최우선 결함:** `fret_labeler.html`은 추가 시 `wire_idx=wires.length`, 삭제 시 전체 `wire_idx=i`로 재번호한다. `two_stage_fret_pipeline.py`는 이를 물리적 `fret_num`으로 사용한다. 중간 프렛 삭제·가림 처리만으로 실제 번호가 바뀔 수 있다. 명시적 물리 번호 입력·중복 검증·미확정 상태를 구현하고, 기존 예시 1개를 다시 검수해야 한다.

추가 우선 결함: 저장 결과에 캔버스 크기가 없어 손 분석이 800×150을 가정한다. 캐시 코너 입력은 live 경로와 같은 검증을 거치지 않는다. 라벨러는 이미지 목록을 manifest 대신 파일명 필터로 구성하여 파생 이미지가 섞일 수 있다. 라벨러 요청 경로와 저장 파일명은 허용 디렉터리 내부인지 검증하고, 저장 payload를 검증해야 한다. YOLO 평가의 split 조회는 기존 데이터셋 경로에 고정되어 있으므로 평가 manifest를 인자로 받아야 한다.

## 6. 개발 파이프라인과 병합 기준

개발 작업은 요구사항·실패 사례 등록 → 데이터/결과 계약 확인 → 작은 구현 변경 → 네트워크 없는 단위검사 → 고정 캐시 회귀검사 → 필요한 경우 새 유료 평가 → 근거와 함께 검토 → 버전 산출물 보존 순서로 수행한다.

1. 프로젝트 버전 관리 범위를 확정하고 Python 환경·직접 의존성·검증된 버전을 기록한다. `.env`와 대용량 데이터/가중치는 소스 이력에 넣지 않는다. 자산은 manifest로 추적한다.
2. import가 API 요청·학습·파일 생성·GUI 실행을 유발하지 않도록 정리한다. 일반 CI에서 `unittest discover`는 실험 분리 전 사용하지 않는다.
3. CI 필수 항목: 구문/정적 검사, 22개 기존 검사, 입력 스키마 검사, 고정 fixture 재생, API 호출 0회 확인. 이후 데이터 계약과 실제 실패를 검증하는 회귀 사례만 추가한다.
4. 캐시 재생 fixture는 새 live 응답 비교와 분리한다. 기하 수정 효과는 동일 응답에서 먼저 비교한다. 모델 변경 효과는 전처리·데이터·평가 기준을 고정하고 여러 번 측정한다.
5. 유료 평가는 명시적 실행 옵션, 호출 상한, 출력 토큰 상한, 재시도 상한, 중단 상태 저장을 갖춘다. 단가 확인 전 금액을 추정하지 않는다. 기존 성공 기록은 자동 재호출하지 않는다.
6. 매 변경은 검증 명령·성공/실패 수·변경 전후 지표·알려진 제한을 남긴다. 실행 성공이나 unknown 감소만으로 정확도 향상을 주장하지 않는다.

현재 사용 가능한 안전한 검증 명령:

```powershell
python -m unittest test_hand_fret_tracker test_fret_geometry test_baze_client -v
python two_stage_fret_pipeline.py sample_images/new_user_fender_maple.jpg --corners-json sample_images/new_guitar_corners.json --frets-json sample_images/perfect_certain_frets.json --out-prefix artifacts/replay/fender
```

첫 명령은 이번 감사에서 통과했다. 두 번째는 기존 CLI의 오프라인 재생 명령이며 이번 감사에서 실행하지 않았다. 두 캐시 옵션을 모두 지정해야 완전한 오프라인 실행이다.

## 7. 단계별 개발 지시와 완료 조건

기간은 인력·라벨링 공급을 확정하기 전의 작업 예상이며 납기 약속이 아니다. 역할은 한 사람이 겸임할 수 있다. 다음 숫자는 기존 실적이 아니라 제안하는 승격 기준이다.

| 순서 | 예상 | 책임 역할 | 반드시 낼 산출물 | 완료 조건 |
|---|---|---|---|---|
| P0-1 | 1~2일 | 플랫폼 | 환경 명세, 명시 테스트 진입점, 실험 실행 분리 | 새 환경에서 22개 테스트 통과, 일반 검사 중 API 0회 |
| P0-2 | 2~3일 | 데이터·기하 | 프렛 라벨러 번호 수정, schema v2, 기존 캐시 변환 | 중간 선 삭제에도 물리 번호 유지. 비표준 캔버스 저장/재로딩 일치. 잘못된 입력 거부 |
| P1-1 | 1~2주 | 데이터·검수 | 초기 100장 원본 manifest·정답 세트 | 50장 개발/20장 선택 검증/30장 잠금 테스트. 같은 촬영·기타·유사 프레임은 같은 분할. 예시 입력은 개발 분할 전용 |
| P1-2 | P1-1 이후 | 비전·평가 | 고정 정지 이미지 benchmark와 오류 분류 | 코너 IoU≥0.90, 코너 오차 중앙값≤지판 폭의 10%, 관측 프렛 선 F1≥0.90, 번호 정확도≥0.95를 잠금 세트에서 확인. 전체/조건별/불확실성을 함께 보고 |
| P1-3 | 병행 | 손 분석·검수 | 손 선택·프렛 후보 평가와 검토 UI | 손 선택 정확도≥0.95, 검토 가능한 후보의 프렛 칸 정확도≥0.90. unknown 비율과 오답률 함께 공개 |
| P2 | 정지 이미지 기준 통과 후 1~2주 | 추적 | timestamp·track ID·손실 수명주기·재검출 | 개발용 10개 클립에서 ID 전환/지터/복구 지연 측정. 손 사라짐 뒤 이전 후보를 새 관측으로 재사용하지 않음. 별도 잠금 클립 평가 |
| P3 | 데이터 확보 후 산정 | 현·접촉·오디오 | 실제 현 검출, 접촉 라벨, 음 시작/끝, 튜닝·카포 처리 | 같은 연주의 동기화 자료에서 접촉·음표·현/프렛 정확도 평가. 열린 현·바레·벤딩·슬라이드 실패 보고 |
| P4 | P3 검증 후 산정 | 제품 | 사용자가 수정 가능한 TAB 초안·내보내기 | 음표 onset/offset F1, 현/프렛 정확도, 1분당 수정 시간으로 사용자 효용 확인 |

초기 100장은 조명·지판 색·가림·시점·좌우잡이·반전·프렛 수를 분산한다. 최소 20%를 독립 이중 검수하고 불일치를 합의한다. 잠금 테스트를 본 뒤 개선에 사용하면 해당 세트는 개발 데이터로 전환하고 새 테스트를 마련한다.

프렛 선 F1은 관측 가능한 정답 선만 대상으로 양쪽 지판 가장자리 오차가 로컬 프렛 간격의 10% 이내인 일대일 매칭으로 계산한다. 번호 정확도는 매칭된 선에 대해 별도 측정하며 미매칭 수를 함께 공개한다. 경계 추정·내부 보간은 별도 오차 지표로 평가한다. 손 선택은 선택 가능한 정답 손이 있는 프레임에서 측정하고 손 없음·모호 사례의 오수락률을 별도 보고한다. 프렛 칸 평가는 손끝 투영 위치 후보에 대한 것으로 실제 접촉 정확도와 구분한다. 작은 초기 테스트의 지표에는 표본 수와 신뢰구간을 붙이고 일반화 주장을 제한한다.

## 8. 당장 착수할 작업 순서

1. 프렛 라벨러의 물리 번호 계약 수정과 기존 exemplar 재검수.
2. 결과 JSON에 스키마·캔버스·원본 해시를 추가하고 캐시 입력 검증 통일.
3. 테스트와 유료 실험 분리, 환경 명세·CI 구축.
4. 원본 이미지 manifest와 촬영 그룹별 데이터 분할 확정.
5. 코너·프렛·손 후보 정답을 구축하고 고정 평가기로 기준선 측정.
6. 위 기준선이 확보된 뒤 영상 추적을 시작. YOLO 재학습과 TAB 확정 출력은 해당 선행 조건 충족 후 진행.

총괄 판단: 더 많은 검출 스크립트를 추가하기보다 데이터 계약, 검수 가능한 결과, 반복 가능한 평가에 개발 자원을 먼저 배정한다. 기존 기하·출처 보존 설계를 중심에 두고 하나의 제품 파이프라인으로 수렴시킨다.
